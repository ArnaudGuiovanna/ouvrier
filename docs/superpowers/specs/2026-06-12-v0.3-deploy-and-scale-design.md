# Design: v0.3 "Deploy & Scale"

**Date**: 2026-06-12
**Status**: approved (synthesized from judged design decisions)
**Type**: feature milestone (three workstreams: state foundation, headless deploy engine, web console)

## Vision

v0.2 made a single Ouvrier worker production-grade (DLQ, observability, approvals,
memory, hardened admin API). v0.3 makes workers **deployable and scalable**:

- **A — Horizontal scaling foundation.** A Postgres state backend next to
  sqlite/memory in `internal/state/factory.go`, cron leader-leases so N replicas
  fire once, and durable runs (step-checkpoint journal + crash recovery) so
  in-flight pipe executions survive restarts.
- **B — Agentless PaaS, specialized for Ouvrier.** `ouvrier deploy <env>` ships a
  single cross-compiled Go binary + systemd unit + env file to any server over
  plain SSH. No Docker, no agent on hosts. Headless-first: works from a fresh
  clone in CI with nothing but an SSH key and an env file.
- **C — Web console launched from the CLI.** `ouvrier console` serves an
  embed.FS SPA on loopback and federates the admin APIs of deployed workers
  through SSH tunnels. Admin ports are never exposed publicly; SSH credentials
  and admin tokens never leave the operator machine / process memory.

MVP cuts: no TLS/domain management (at most an "install Caddy" option later),
no rolling updates (v0.3.x), no deterministic LLM-transcript replay, no
encrypted env files, no `ouvrier deploy docker` evolution.

## Sequencing

1. **State foundation** — Postgres store → lease machinery (shared by cron and
   durable runs) → cron leader-leases → durable runs. SQLite schema versions:
   leases land as schema v5, durable-run tables as v6. Postgres migrations are
   versioned independently in `postgres_migrations.go`.
2. **Headless deploy engine** — `internal/deploy` package + pip.yaml `deploy:`
   registry → host-key pinning → admin listener split (`OUVRIER_ADMIN_ADDR`,
   needed because deploy templates remote env files) → systemd/remote layout →
   `ouvrier deploy <env>` end-to-end → rollback + deployments inventory.
3. **Web console** — tunnel manager → headless `--worker/--all` parity on
   existing CLI commands → `ouvrier console` SPA. The UI is strictly a thin
   layer over the same `internal/deploy` / `internal/adminapi` code paths the
   CLI uses; parity is enforced by test.

## 1. Postgres state backend

`internal/state/postgres_store.go` plus per-feature siblings mirroring the
`sqlite_*.go` layout (`postgres_execution.go`, `postgres_event.go`,
`postgres_approval.go`, `postgres_idempotency.go`, `postgres_memory.go`,
`postgres_session.go`, `postgres_violation.go`), sharing the existing
`normalizeMemory`/`normalizeApproval`/redaction helpers unchanged.

- **Driver**: `github.com/jackc/pgx/v5` via `pgx/v5/stdlib` through
  `database/sql` — pure Go, `CGO_ENABLED=0`-safe, structurally parallel to
  `SQLiteStore`. `$1` placeholders written directly; no query-abstraction layer.
- **Config**: `OUVRIER_STATE_BACKEND=postgres` + new `OUVRIER_STATE_DSN`
  (constants in `internal/state/factory.go`, mirrored in `internal/envnames`).
  Missing DSN is a startup error naming both vars. The DSN is secret-bearing:
  never logged; all errors wrapped with the fixed prefix
  `"postgres state store: ..."`; a unit test asserts no error string contains
  the DSN. Warn at startup when `sslmode=disable` and `OUVRIER_ENV != dev`;
  docs default to `verify-full`.
- **Pool**: MaxOpenConns 10 (override `OUVRIER_STATE_MAX_CONNS`), MaxIdleConns
  5, ConnMaxLifetime 30m, ConnMaxIdleTime 5m, `statement_timeout=10s`, 5s
  `PingContext` at startup. `sql.DBStats` exposed via `/admin/health` when
  backend=postgres.
- **Schema**: same `ouvrier_*` table names. `TIMESTAMPTZ` in UTC (native time
  predicates for the lease/stale-run queries that follow; SQLite's
  lexicographic TEXT quirk is not exported). `BIGINT` for `max_wallclock_ns`
  and counts. Event payloads stay **TEXT, not JSONB** — JSON strings must
  round-trip byte-for-byte. `seq` via IDENTITY on approvals.
- **Migrations**: ordered steps in `postgres_migrations.go`, recorded in
  `ouvrier_schema_migrations(version, applied_at)`, executed under
  `pg_advisory_xact_lock`. `OUVRIER_STATE_MIGRATE=auto|off` (default auto) +
  `ouvrier state migrate` CLI for DML-only production roles. v0.3.x migrations
  stay additive-only.
- **Concurrency**: idempotency via single-statement
  `INSERT .. ON CONFLICT DO UPDATE .. RETURNING exec_id, (xmax=0)`; approvals
  via `UPDATE .. WHERE status='pending' RETURNING`; event IDs via a single-row
  `ouvrier_event_counter` table (`UPDATE .. RETURNING` for auto-assign,
  `UPDATE .. WHERE last_id < $1` for explicit-ID rejection), seeded from
  `MAX(id)` in the migration — cross-replica collision-free for both ID paths.
- **Tests**: existing conformance suites + ported `sqlite_store_test.go` cases
  (idempotency x32, monotonicity, reopen) gated on
  `OUVRIER_TEST_POSTGRES_DSN` (unset ⇒ `t.Skip`); per-test ephemeral schemas
  via `search_path`, dropped in cleanup. A `timestampsEqual` helper with 1µs
  tolerance used **only** in Postgres-side comparisons (SQLite assertions stay
  exact). A two-pool test (two `*sql.DB` pools, one database) races idempotency
  and approval resolution to simulate two replicas. CI gains a **required**
  `postgres:16-alpine` service job.

## 2. Cron leader-leases

**State layer** (additive; the `Store` interface is untouched): optional
`LeaseStore` interface discovered via `store.(state.LeaseStore)`:

```go
AcquireLease(ctx, name, holder string, ttl time.Duration) (Lease, bool, error)
RenewLease(ctx, name, holder string, fence uint64, ttl time.Duration) (Lease, bool, error)
ReleaseLease(ctx, name, holder string, fence uint64) error
Leases(ctx) ([]Lease, error) // observability
```

`Lease{Name, Holder string; Fence uint64; AcquiredAt, RenewedAt, ExpiresAt time.Time}`.
Table `leases(name PK, holder, fence BIGINT, acquired_at, renewed_at, expires_at)`.
Acquire is one atomic `INSERT .. ON CONFLICT(name) DO UPDATE .. WHERE
expires_at < DBNOW RETURNING ..` — no holder self-reacquire clause;
fence-checked Renew is the only extension path. All expiry comparisons use
**database time** (`now()` in Postgres, `strftime` in SQLite); holders treat
leases as locally dead at 80% of TTL. Real implementations on memory and
SQLite (schema v5) so one `lease_conformance_test.go` (16-contender race,
fence monotonicity, expiry takeover, release) covers all backends.

**Naming**: lease name `cron:<sha256-8 of trigger expr>:<occurrence-index among
same-expr plans>` — stable under unrelated plan reordering. Holder:
`<hostname>-<rand8>`, overridable via `OUVRIER_REPLICA_ID`.

**Runtime hook**: new `runtime_cron_lease.go` wraps `runCronLoop` in a
follower/leader state machine. Followers poll AcquireLease every 15s ±20%
jitter; the leader runs the existing timer loop, renews at TTL/3 in the
background, **and synchronously renews immediately before each fire** —
renewal failure means skip the fire, emit `cron_lease_lost`, drop to follower.
At-most-once; missed ticks are never backfilled; in-flight runs are never
cancelled. Per-fire dedupe via existing `ReserveIdempotency` with key
`cron_fire:<leaseName>:<scheduledAt RFC3339>`. Because
`intervalCronSchedule.Next` is relative to local now, `@every` fires are
aligned to epoch multiples of the interval whenever a LeaseStore is active, so
`scheduledAt` matches across replicas. Graceful shutdown calls ReleaseLease
for instant failover. No LeaseStore / nil store ⇒ v0.2 unleased behavior.

**Config**: fixed TTL 30s (no knob); only `OUVRIER_REPLICA_ID` and the
`OUVRIER_CRON_LEASE=off` escape hatch in `internal/envnames`.

**Observability**: events `cron_lease_acquired`/`cron_lease_lost`/
`cron_tick_skipped` (holder, fence, expires_at); fence stamped into cron fire
event payloads; `/admin/health` gains
`cron_leases: [{name, holder, fence, expires_at, is_self}]`, surfaced by
`ouvrier status`. Postgres lease conformance must run against real Postgres in
CI before multi-replica is documented as supported.

## 3. Durable runs (journal/replay)

Step-checkpoint journal, opt-in via `OUVRIER_DURABLE_RUNS=1` (default off);
startup guard refuses the memory backend.

**Granularity**: checkpoint after each completed top-level pipe step,
persisting only the inter-step output string from `runStepsResult` (redacted).
No `provider.Message` transcripts, no tool results. Parallel/Map checkpoint as
one unit.

**Schema** (SQLite v6 + Postgres migration), behind the existing `Store`
interface with a conformance suite:

- `run_journal(exec_id PK, plan_key, plan_hash, trigger_kind, input, created_at)`
  — `plan_hash` hashes the compiled steps; input is redacted.
- `run_checkpoints((exec_id, step_index) PK, output, completed_at)` — redacted.
- `tool_intents((exec_id, tool_call_id) PK, step_index, tool_name, effect,
  idem_key, started_at, completed_at NULL)` — metadata only, consistent with
  the v0.2 redaction posture.

**Side-effect safety**: write a `tool_intent` row before executing any
non-read tool; mark completed after. On recovery, if the interrupted step has
open intents with effect idempotent/side_effecting, do **not** auto-replay:
mark the run failed with `EventReplayIndeterminateTool`; the operator inspects
via `GET /admin/runs?status=orphaned` and forces replay via
`POST /admin/runs/{execID}/recover`. Read-only-intent steps replay
automatically. Fix `ReserveIdempotency` consumers (`internal/tools/idempotency.go`)
so a reservation held by the **same exec_id** is treated as success during a
recovered run (today it errors).

**Coordination**: recovery claims are run leases on the same `LeaseStore`
machinery as cron leader-leases; durable runs heartbeat their lease while
executing, recovery claims only expired leases. Recovery runs with jitter and
a concurrency cap (cron worker-pool pattern).

**Semantics**: at-least-once per step for read-only work; fail-loud for
indeterminate writes. `plan_hash` mismatch (pipeline edited between deploys) ⇒
clean `EventRunAbandoned`. Sync reply/SSE runs are abandoned on recovery
(client gone). Cross-restart approval resume: the in-memory registry stays the
fast path; the fallback replays the suspended step with an `args_hash`
auto-allow on already-approved records (hash inputs must match
`idempotency.go`'s hashing).

**Retention**: prune journal/checkpoints/intents in `finishPipelineExecution`
on success; keep failed/suspended runs for `OUVRIER_DURABLE_RETENTION`
(default 72h); prune failures emit events and surface in `/admin/health`.

**Cut**: conversation/provider-response journaling, mid-step resume,
sub-branch checkpoints, CLI commands, journal compaction. The journal table
leaves room for `provider_response` record kinds in a future
deterministic-replay upgrade.

## 4. Server registry & SSH credentials

The registry is the existing pip.yaml `deploy:` block — committed, secret-free,
team-shared. No user-level server registry, no alias indirection:
`ouvrier deploy <env>` must work from a fresh clone + ssh key + env file
(headless/CI-first).

```yaml
deploy:
  staging:
    hosts: [deploy@stg-1.example.com]
    port: 22          # optional
    path: /opt/ouvrier/myworker   # optional
    service: ouvrier-myworker     # optional
    identity: ~/.ssh/ci_ed25519   # optional, for agent-less CI
  prod:
    hosts: [deploy@prod-1, deploy@prod-2]   # hosts may be ~/.ssh/config aliases
```

Parsed by extending `parsePipYAML()` in `internal/cli/pipyaml.go` (no YAML
dependency). Per-operator differences (jump hosts, usernames) live in
`~/.ssh/config`.

- **SSH auth**: zero credentials stored by Ouvrier, ever. Reuse the
  `remoteRunner` ssh/scp seam; always pass `-o BatchMode=yes
  -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no`, plus `-i`
  from `identity:`/`--identity`.
- **Host-key pinning**: `ouvrier server trust <host>` runs `ssh-keyscan`,
  shows the SHA256 fingerprint, requires interactive confirm or
  `--fingerprint` (CI), and appends to a **committed** `ouvrier.known_hosts`.
  Every deploy uses `-o UserKnownHostsFile=ouvrier.known_hosts
  -o StrictHostKeyChecking=yes`; a changed key is a hard error naming
  `server trust --rotate`.
- **Secrets**: per-env dotenv at project root (`.env.staging`, `.env.prod`,
  fallback `.env`), overridable via `--env-file`/`OUVRIER_DEPLOY_ENV_FILE`.
  Pre-flight validates against `env.required` + `OUVRIER_ADMIN_TOKEN` using
  the existing `parseDotenv` (report missing **names** only); hard-fail if the
  env file is git-tracked; scaffold gitignores `.env*`. Ship via safe ordering:
  upload to a temp path, chmod 0640, then rename — fixing the umask window in
  today's upload-then-chmod flow in `deploy_ssh.go`.
- **Multi-host**: sequential, health-check each, abort on first failure
  (per-host rollback); loud mixed-version summary. Deploying to
  prod/production requires `--yes` or interactive confirm.
- **Code layout**: target/env resolution and the deployments inventory live in
  a new `internal/deploy` package so the console reuses them without importing
  CLI command code.

**Deployments inventory / fleet file** (reconciling the registry, federation,
and console decisions into one file): `~/.config/ouvrier/deployments.json`
(0600, atomic tmp+rename, stdlib JSON, `"version": 1`; override via
`OUVRIER_CONFIG_DIR` / `OUVRIER_FLEET_PATH`). Upserted per successful host
deploy with: name, host, user, port, path, service, admin_addr, health_path,
binary sha256, git rev, deployed_at, result. **No secrets ever.** It is a
disposable cache for `ouvrier console`/`fleet` tunnels; live `/admin/health`
is truth. Minimal `ouvrier fleet ls|rm` commands manage it. User-level (not
project-local) so one console can federate workers across projects.

Deferred: `server check`, separate deploys.jsonl audit log, encrypted env
files (v0.3.x).

## 5. Remote host layout & lifecycle

Host layout under root `/opt/ouvrier/<name>` (override `--path` / pip.yaml
`deploy.path`):

```
releases/<UTCts>-<shortsha>/{bin/<name>, skills/, RELEASE.json}  # immutable
current -> releases/<id>      # swap: ln -sfn .. current.tmp && mv -T current.tmp current
shared/.env                   # root:svc 0640 — worker reads, cannot rewrite its secrets
shared/state/state.db
deploys.log                   # append-only: release id + previous `current` target
.deploy.lock                  # remote flock held for the whole deploy; self-releases
```

`RELEASE.json` records sha256, git sha, go version, builder, deploy time (the
console lists releases from it). Preflight verifies GNU `mv -T`, else falls
back to `ln -sfn` with a documented micro-race. Rollback resolves the previous
release from `deploys.log`, never from timestamp sort (clock-skew-proof).

**systemd**: system unit `/etc/systemd/system/ouvrier-<name>.service` rendered
by new `internal/deploy/systemd_unit.go`, installed only when its sha256
differs. Dedicated per-worker system user `ouvrier-<name>` (nologin), never
root. `Environment=OUVRIER_STATE_PATH=<root>/shared/state/state.db` placed
**before** `EnvironmentFile=<root>/shared/.env` (default survives release
swaps; operator .env can still point at Postgres). `Restart=always`,
`RestartSec=2s`, `StartLimitIntervalSec=60`, `StartLimitBurst=5`. Hardening on
by default: `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome=yes`,
`PrivateTmp`, `UMask=0077`, `ReadWritePaths=<root>/shared`; escape hatch via
pip.yaml `deploy.sandbox: off` or `--unit-sandbox=off`.

**`ouvrier deploy <env>` step by step** (all ssh `-o BatchMode=yes`, existing
`remoteRunner` seam; `deploy ssh --host user@host` kept as alias):

1. Local preflight: parse pip.yaml, require env file, validate `env.required`
   keys, `staticBuildForDeploy` (add `--target` passthrough for arm64),
   compute sha256.
2. Remote preflight (one ssh): `sudo -n true` probe with actionable error,
   systemd check, create user, mkdir layout, take flock.
3. Upload release; verify remote sha256; chmod 0755.
4. Upload .env atomically (temp + chmod 0640 + rename), including
   `OUVRIER_ADMIN_ADDR=127.0.0.1:9090` by default (see §6).
5. Install unit if changed + daemon-reload + enable; `--print-sudoers` emits a
   least-privilege sudoers snippet.
6. Symlink swap; `sudo systemctl restart`.
7. Health gate: on-host curl to `127.0.0.1<admin>/admin/health` (10
   attempts/30s), token passed via curl stdin config (`-K -`), never in argv.
8. Success: append `deploys.log`; prune to `--keep` 5 with the rm list built
   in Go from `ls -1` output, each path quoted (no `head|xargs rm -rf`); upsert
   the deployments inventory. Failure: dump `journalctl -u <svc> -n 50`,
   repoint `current` to the recorded previous, restart, re-check, exit nonzero
   with both errors; a first deploy (no previous) degrades to stop+report.

`ouvrier deploy rollback --host ...` / `ouvrier deploy rollback <env>`: no
build; resolve previous from `deploys.log`, swap, restart, health-check.

## 6. Admin API federation over SSH tunnels

**Worker prerequisite — split admin listener.** New `OUVRIER_ADMIN_ADDR` in
`internal/envnames`. When set, `runtime_http.go` starts a second loopback
listener with its own mux; `registerHTTPAdminRoutes()` (plus `/metrics`)
moves there. Unset preserves v0.2 shared-port behavior. `ouvrier deploy`
writes `OUVRIER_ADMIN_ADDR=127.0.0.1:9090` into the remote .env by default and
refuses to register a publicly-shared admin target without
`--allow-shared-admin`. Without this split, "admin never exposed" is
impossible (verified: admin routes share the public mux today,
`runtime_http.go:100-118`, `routes.go:149`).

**Tunnels.** New `internal/tunnel` Manager shelling out to system OpenSSH —
one `ssh -N -o BatchMode=yes -o ExitOnForwardFailure=yes
-o ServerAliveInterval=15` process per worker — forwarding to unix sockets in
`$XDG_RUNTIME_DIR/ouvrier/tunnels/<name>.sock` (dir 0700,
unlink-before-spawn, flock'd); `--tcp-tunnels` falls back to ephemeral
loopback ports (Windows; freeport via listen-then-close, never parse `-L 0`
output). Explicit state machine connecting/up/degraded/down with last error
and ssh stderr surfaced verbatim; jittered backoff 1s→30s; lazy start so one
dead host never blocks first paint; idle close after 5m with in-flight request
refcounting. A `tunnelRunner` interface mirrors `remoteRunner` for tests, plus
one opt-in integration test against a local sshd.

**Tokens.** At tunnel open, fetch the remote `<path>/shared/.env` over SSH,
parse with the existing dotenv parser, hold `OUVRIER_ADMIN_TOKEN` **in memory
only** (masked everywhere). On 401/403 re-fetch once (rotation), then mark
`auth_failed` per target. Fallbacks: `--token`, local env var. SSH access
remains the only operator credential; nothing token-shaped touches disk.

**Headless parity.** `--worker <name>` / `--all` flags on existing
`status`/`logs`/`trace` commands use Manager one-shot tunnels with the same
`adminClient` (extracted to `internal/adminapi`). The console UI is strictly a
layer over this path.

## 7. Web console

`ouvrier console` (new case in `internal/cli/app.go`,
`internal/cli/console.go`; flags `--addr` default `127.0.0.1:7333` /
`OUVRIER_CONSOLE_ADDR`, `--fleet` (inventory path override), `--no-open`)
starts a loopback-only server from new package `internal/console` (`server.go`,
`api.go`, `fleet.go`, `assets/` via `//go:embed`; tunnels via
`internal/tunnel`).

- **SPA, no build chain**: vendored Preact + HTM ESM files in
  `assets/vendor/`, plain ES modules served from embed.FS; optional dev-only
  `tsc --checkJs` with JSDoc types. No npm/bundler in repo or CI. CSP
  `default-src 'self'; connect-src 'self'` + `X-Frame-Options: DENY` make the
  no-CDN rule structural. MVP pages: fleet overview, worker detail
  (status/plans/traces, SSE event tail, approvals, manual trigger), deploy
  with streamed progress.
- **Local API**: `GET /api/v1/fleet` (inventory + tunnel state);
  `POST /api/v1/workers/{name}/deploy` (JSONL/SSE progress, calls
  `internal/deploy.DeploySSH(ctx, Opts, ProgressWriter)`);
  `ANY /api/v1/workers/{name}/admin/{rest...}` via `httputil.ReverseProxy`
  dialing the unix socket with `FlushInterval=-1` for SSE, Authorization
  injected server-side (tokens never reach the browser), strict method/path
  allowlist (all GETs + POST trigger/approvals/streams-replay) kept adjacent
  to `registerHTTPAdminRoutes` with a cross-check test;
  `GET /api/v1/overview` concurrent fan-out with 5s per-target timeout and
  partial results; `GET /api/v1/events` fan-in of per-worker
  `/admin/events?format=jsonl&follow=true` tagged with worker name, per-worker
  `after_id` cursors for lossless reconnect, synthetic
  `console.worker_unreachable` events for down targets.
- **Parity by construction**: `deploy_ssh.go` body extracted into
  `internal/deploy`, `admin_client.go` into `internal/adminapi`; CLI and
  console call the same functions. Console handlers are
  decode → ops/proxy → encode only. A `parity_test.go` asserts every
  `/api/v1` route maps to a documented CLI command.
- **Security**: refuse non-loopback bind unless `OUVRIER_CONSOLE_INSECURE=1`
  (mirror `checkAdminExposure`); random 256-bit per-session token printed at
  start and delivered via URL fragment, held in memory, sent as
  `Authorization: Bearer` (consistent with `authorizeAdmin`), constant-time
  compare; **zero cookies** (CSRF impossible); Host-header allowlist and
  Origin rejection (DNS-rebinding defense); `Cache-Control: no-store`. The
  auth layer lands before any deploy-capable route.

## Consolidated open questions

**State foundation**
1. Is microsecond timestamp precision acceptable for executions/events/
   approvals, or will the durable-run journal need byte-exact timestamp
   round-trips for deterministic replay? (Only this would flip TIMESTAMPTZ
   back to TEXT.)
2. Will the durable-run journal write checkpoints through `AddEvent`? If so,
   the serialized event counter needs sizing, or the journal gets its own
   sequence (current design: dedicated tables, own keys — but confirm).
3. Should `ouvrier state migrate` + `OUVRIER_STATE_MIGRATE=off` ship in
   v0.3.0, or is auto-migrate-only acceptable for the MVP?
4. Is at-most-once cron acceptable to document ("a tick may be skipped during
   failover, up to ~TTL+jitter, never backfilled"), or do some users need a
   catch-up/backfill option?
5. Should cron plans get a stable user-facing ID in pip.yaml now (also useful
   for admin API and rolling updates), or is expr-hash naming acceptable until
   v0.3.x?
6. Is a brief double-fire window during mixed-version rolling deploys
   (different lease names across binaries) acceptable to document?
7. On recovery of an indeterminate write-tool, should the default be
   fail-the-run (operator forces via `POST /admin/runs/{id}/recover`), or
   automatically re-gate through the existing human approval flow?
8. Is persisting redacted step inputs/outputs at rest a new acceptable data
   class, or is a per-plan/per-step opt-out needed for sensitive pipelines?

**Deploy engine**
9. Is committing hostnames/users in pip.yaml acceptable for target users, or
   do some teams need a gitignored override (e.g. `pip.local.yaml`)?
10. Should deploy hard-require `OUVRIER_ADMIN_TOKEN` in the env file, or is
    warn-and-proceed acceptable for fire-and-forget workers?
11. Does the nested `deploy.<env>` schema stay within what the hand-rolled
    YAML parser should carry, or is this the moment to adopt a YAML library?
12. Rollback/.env consistency: should each release snapshot the .env it was
    deployed with (rollback restores code+env together, but secrets then live
    in `releases/` until pruned), or does rollback intentionally keep the
    latest .env?
13. Does `ouvrier deploy docker` stay in v0.3 given the "no Docker" stance, or
    is it deprecated/frozen while SSH becomes the default deploy path?
14. Is requiring sudo (even scoped via `--print-sudoers`) acceptable, or does
    v0.3 need a root-less degraded mode (user unit + lingering)?

**Console / federation**
15. Deployments inventory location: user-level `~/.config/ouvrier/
    deployments.json` (one console across projects — current design) vs
    project-local `.ouvrier/fleet.json` (committed host inventory)? The three
    judged decisions split on this; user-level is the synthesis, confirm.
16. When `OUVRIER_ADMIN_ADDR` is set, should `/metrics` move entirely to the
    admin listener, or optionally stay public for Prometheus scrapers that
    cannot traverse SSH?
17. Is Windows operator support in scope for v0.3 (decides whether the
    `--tcp-tunnels` fallback ships in the MVP)?
18. How ambitious is the v0.3.x console roadmap? If rich features (charts,
    live editing) come soon, starting with an esbuild/TypeScript pipeline now
    may be cheaper than migrating off no-build Preact+HTM later.

## Success criteria

1. A two-replica worker on Postgres passes the conformance + two-pool race
   suites, fires each cron tick exactly once across replicas, and recovers
   crashed read-only runs without operator action.
2. `git clone && ouvrier server trust <host> && ouvrier deploy staging` from a
   clean CI runner produces a healthy systemd service, with rollback on a
   failing health gate.
3. `ouvrier console` shows live status/events of all deployed workers with no
   admin port exposed publicly and no token or SSH credential written to disk.
4. Every console capability has a documented headless CLI equivalent,
   enforced by `parity_test.go`.
