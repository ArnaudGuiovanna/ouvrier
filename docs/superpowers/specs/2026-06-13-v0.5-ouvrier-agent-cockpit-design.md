# Design: v0.5 "Ouvrier Agent Cockpit"

**Date**: 2026-06-13
**Status**: accepted; initial implementation in progress
**Type**: corrective product spec after v0.4.0
**Follow-up**: the concrete TUI/streaming rendering model (the part that makes it
feel like Pi) is specified and implemented in
[v0.5.1 Cockpit TUI Realization](2026-06-14-v0.5.1-cockpit-tui-realization.md).

## Problem Statement

`ouvrier operate` v0.4 shipped the right nouns but the wrong product shape. It
is a workflow orchestrator with subcommands and a thin Bubble Tea screen. The
intended product is different: a terminal-native agentic coding cockpit, in the
same category as Pi, Codex, or Claude Code, specialized for manufacturing
Ouvrier workers.

The user should be able to run:

```sh
ouvrier operate
```

Then type:

```text
Create a worker that receives POST /tickets, loads the ticket from our CRM,
triages it with a governed read-only tool, stores the result, and deploy it to
staging.
```

The harness should then create the worker project, plan, edit files, inspect
the Ouvrier API, run tests, review the code, repair issues, build the binary,
and transfer it to a server, while keeping every action visible and auditable
inside one terminal interface.

That is the product. It is not `operate patch --goal ...` plus separate
commands.

## Reference Model

Pi is the closest conceptual reference, not a dependency to vendor blindly.
The public Pi repository describes a mono repo with an interactive coding
agent CLI, an agent runtime with tool calling and state management, a unified
multi-provider LLM API, and a TUI library. The installed Pi CLI exposes
interactive sessions, provider/model selection, subscription login, skills,
extensions, prompt templates, themes, built-in read/bash/edit/write tools,
session resume/fork/export, JSON/RPC modes, and slash-command-like workflows.

Ouvrier should transpose that product pattern into Go and narrow it to one
domain: building Ouvrier workers correctly.

What to copy conceptually:

- a real prompt composer, not a wizard-only UI;
- streaming transcript with model deltas and tool cards;
- persistent sessions with resume, continue, fork, export;
- provider/auth abstraction with a first-class login command;
- tool allowlists and deny lists;
- skills/prompt packs loaded into the agent context;
- extension-like internal hooks, but governed by Ouvrier policy;
- read-only review mode and write-capable edit mode;
- structured lifecycle events for TUI rendering and replay.

What not to copy:

- unbounded user-process permissions by default;
- generic coding-agent scope as the product center;
- TypeScript/npm runtime inside Ouvrier;
- direct storage or reverse engineering of third-party subscription tokens;
- opaque file generation that bypasses Ouvrier's Go/scaffold/deploy engines.

## Product Definition

`ouvrier operate` is the local Ouvrier worker factory.

It is:

- a coding agent harness;
- a terminal UI;
- a Codex-authenticated agent client;
- an Ouvrier API expert;
- a worker scaffold/edit/review/build/deploy environment;
- an audit log.

It is not:

- a web IDE;
- the worker runtime;
- the web console;
- a generic coding agent;
- a remote builder service in v0.5.

The web console remains fleet observation and remote operations:

- observe workers;
- stream logs/traces;
- approve suspended runtime actions;
- trigger deployed workers;
- watch deploy progress.

The terminal cockpit owns construction:

- create worker;
- edit worker;
- review code;
- repair code;
- build binary;
- transfer/deploy.

## User Experience

### First Run

```sh
ouvrier operate
```

If no Codex auth is configured:

```text
Codex authentication required

Use ChatGPT/Codex subscription auth:
  > /login codex

Or use a provider API key:
  > /login openai
  > /login anthropic
```

`/login codex` launches or delegates to the official Codex login flow. Ouvrier
stores only driver metadata, not the Codex token. If Codex CLI/app-server owns
the credential, Ouvrier records "codex profile exists" and probes it on use.

After auth, the operator lands in a composer:

```text
Ouvrier Agent Cockpit
cwd: ~/workers
model: codex/gpt-5.5 high
mode: build-worker

What do you want to build?
> _
```

### Create Worker From Prompt

The user types a natural language goal. The agent does not ask the user to pick
flags first. It infers a worker plan and asks only for missing high-value
decisions:

```text
I can build this worker.

Plan:
1. Scaffold worker ticket-triage with POST /tickets.
2. Add CRM load_ticket read-only tool.
3. Add triage pipeline with typed Triage output.
4. Add tests for load_ticket and pipeline wiring.
5. Run audit gates, review, build linux/amd64.
6. Deploy to staging after approval.

Missing:
- CRM base URL/env var name?
- deploy env: staging from pip.yaml, or create one?

[Enter] approve plan   [e] edit plan   [a] answer missing fields
```

Once approved, the agent uses tools. The transcript shows tool cards:

```text
tool scaffold_worker
  name: ticket-triage
  trigger: POST /tickets
  model: anthropic/claude-sonnet-4-6
  result: created ./ticket-triage

tool read_doc
  source: docs/api.md
  lines: Reply(JSON[T]), Tool, ReadOnly

tool patch_file
  file: main.go
  result: +83 -14

tool run_audit
  gofmt: pass
  go test ./...: pass
  go vet ./...: pass
  manifest: pass
```

### Review And Repair

The operator can type:

```text
review this worker for security and governance
```

The harness switches to read-only review mode. Findings appear in an inbox:

```text
Review findings
1 high     tools/crm.go:42  HTTP client has no timeout
2 medium   main.go:68       tool should be marked Idempotent with ticket ID

[1] open   [f] fix selected   [a] accept risk   [x] dismiss
```

When the user asks to fix, the finding becomes a scoped edit goal. The fix
turn still goes through plan -> patch -> diff -> audit -> review.

### Build

The user can type:

```text
build this for linux/amd64
```

The agent calls the build tool, not arbitrary shell, unless the policy permits
shell. `build.json` records:

- binary path;
- target;
- sha256;
- Go version;
- commit/worktree state;
- audit and review status.

### Transfer

The user can type:

```text
deploy to staging
```

The harness resolves `pip.yaml`, shows the transfer plan, and requires
approval:

```text
Transfer plan
env: staging
hosts: deploy@stg-1.example.com
target: linux/amd64
audit: pass
review: pass
known_hosts: pinned

[Enter] deploy   [d] diff   [b] rebuild   [q] cancel
```

Transfer uses the existing deploy engine. It streams progress into the same
transcript and writes `transfer.json`.

## Interaction Model

The TUI has four permanent regions:

1. **Transcript** - chronological messages, tool calls, approvals, reviews,
   audit output, build/deploy progress.
2. **Composer** - bottom prompt input with slash commands, natural language,
   file mentions, and paste mode.
3. **Side drawer** - session details, worker manifest, diff tree, review
   finding, deploy target, or help.
4. **Status bar** - model, auth profile, cwd, mode, branch, gate status, cost
   or token estimate, current task.

Keyboard expectations:

- `Enter`: submit prompt or approve focused confirmation.
- `Esc`: cancel current modal or interrupt streaming turn.
- `Ctrl+C`: graceful quit with session saved.
- `Ctrl+R`: resume/fork session picker.
- `Ctrl+P`: model/profile picker.
- `Ctrl+T`: tool policy picker.
- `Tab`: cycle focus transcript/composer/drawer.
- `/`: slash command prefix.
- `?`: command palette/help.

Slash commands:

```text
/login codex
/logout codex
/model codex/gpt-5.5:high
/new worker
/open worker
/review [scope]
/fix [finding-id]
/audit
/build [target]
/deploy [env]
/diff
/checkpoint
/rollback
/resume
/fork
/tools
/policy
/export
```

Natural language should cover the same capabilities. Slash commands are
accelerators, not the primary interface.

## Architecture

The critical architecture rule is separation between the agent kernel and its
I/O modes. The TUI is only one client of the kernel.

```text
operator prompt
  -> OperateSession
  -> AgentRuntime
  -> ModelSession
  -> ToolRegistry / ToolExecutor / OperatePolicy
  -> EventStore
  -> TUI | print | json | rpc
```

This mirrors the useful Pi shape: one session/runtime can power interactive
mode, non-interactive print mode, and machine RPC. Ouvrier should not bake the
agent loop into Bubble Tea screens.

### Packages

```text
internal/operate/agent
  AgentRuntime, turn loop, tool calling, compaction, retries

internal/operate/auth
  AuthBroker, CodexLogin, provider profile store, auth probes

internal/operate/promptpack
  Ouvrier API prompt pack, syntax handbook pack, examples pack, policy pack

internal/operate/tools
  native Ouvrier tools exposed to the agent

internal/operate/workspace
  workspace discovery, scaffold, worktree/checkpoint, git status, diff

internal/operate/review
  findings, review inbox, finding-to-fix context

internal/operate/audit
  deterministic gates and structured diagnostics

internal/operate/session
  persistent transcript, artifacts, events, resume/fork/export

internal/operate/rpc
  JSONL protocol for external clients and tests

internal/operate/tui
  Bubble Tea cockpit, transcript, tool cards, composer, drawer

internal/operate/codex
  Codex provider/session driver
```

The existing v0.4 packages can be migrated into these narrower packages rather
than deleted wholesale, but the product center changes from command
orchestration to agent runtime.

### Core Interfaces

```go
type AgentRuntime interface {
    Start(ctx context.Context, req StartRequest) (*Session, error)
    Prompt(ctx context.Context, sessionID string, msg UserMessage) error
    Steer(ctx context.Context, sessionID string, msg UserMessage) error
    FollowUp(ctx context.Context, sessionID string, msg UserMessage) error
    Interrupt(ctx context.Context, sessionID string) error
    Compact(ctx context.Context, sessionID string) error
    Resume(ctx context.Context, sessionID string) (*Session, error)
    Fork(ctx context.Context, sessionID string) (*Session, error)
    Subscribe(sessionID string) (<-chan Event, error)
}

type ModelSession interface {
    Send(ctx context.Context, req ModelRequest, stream EventSink) (ModelResult, error)
    Close() error
}

type Tool interface {
    Name() string
    Description() string
    Schema() JSONSchema
    Policy() ToolPolicy
    Execute(ctx context.Context, call ToolCall, stream EventSink) (ToolResult, error)
}

type AuthBroker interface {
    Profiles(ctx context.Context) ([]AuthProfile, error)
    Login(ctx context.Context, provider string, ui LoginUI) (AuthProfile, error)
    Probe(ctx context.Context, profile AuthProfile) (AuthStatus, error)
    Logout(ctx context.Context, profile string) error
}
```

### Agent Loop

Each user prompt enters a real tool-calling loop:

1. build context from prompt pack, workspace state, session memory, selected
   files, manifest, docs;
2. send model request with tools and policy;
3. stream assistant deltas into transcript;
4. receive tool calls;
5. authorize each call through `OperatePolicy`;
6. execute tools through `ToolExecutor`;
7. append tool results to transcript;
8. continue until the model emits a terminal outcome;
9. run post-turn observers: diff capture, review hints, gate suggestions;
10. persist all events.

No final text answer counts as completion for creation/editing. Completion
requires observed files, diff, gates, and an explicit session state transition.

### Prompt, Steer, Follow-Up, Abort

The runtime must distinguish four operator inputs:

- **Prompt**: starts a new agent turn when idle.
- **Steer**: interrupts the current streaming assistant/tool context with
  guidance that should be considered before continuing, without discarding the
  turn.
- **Follow-up**: queues the message after the current turn settles.
- **Abort**: cancels the model stream or active tool, records an interrupted
  event, and leaves the workspace recoverable.

This is mandatory for a real cockpit. If a long patch/build/review is running,
the operator must be able to say "stop, use Accepted reply instead" or "after
this, also add a cron trigger" without killing the terminal process.

### Codex Auth And Driver

The target auth story is "like Pi": subscription login is first-class in the
terminal.

Supported modes:

1. **Codex CLI bridge** (v0.5 MVP)
   - `ouvrier operate /login codex` launches `codex login` or points the user
     to it.
   - `CodexAuthBroker` runs `codex auth status` or a small authenticated probe.
   - `CodexModelSession` uses official Codex CLI transports only. `codex exec
     --json` is acceptable for initial simple turns. A richer transport can be
     added only when the official Codex surface supports streaming multi-turn
     state and tool-call control cleanly.
   - Ouvrier never reads or stores Codex access tokens.

2. **Provider API key mode**
   - optional fallback for OpenAI/Anthropic/etc. through Ouvrier's provider
     adapters or a dedicated operate provider layer;
   - keys can come from env vars or an Ouvrier auth file with `0600`
     permissions;
   - secrets are redacted in transcript and artifacts.

3. **Direct subscription mode** (future only)
   - only if an official, documented OpenAI/Codex auth API exists for this
     use. No token scraping.

The driver must expose capabilities:

```json
{
  "provider": "codex",
  "transport": "app-server",
  "authenticated": true,
  "models": ["gpt-5.5", "gpt-5.4"],
  "supports_tools": true,
  "supports_streaming": true,
  "supports_interrupt": true,
  "supports_resume": true
}
```

If `codex exec` cannot offer real tool-call control, it is acceptable only as
an MVP bootstrap. The desired architecture is an Ouvrier-owned tool loop with a
model/session transport that can stream and request tool calls.

Do not over-invest in an HTTP app-server before the local JSONL/RPC contract is
stable. Pi's installed CLI exposes `--mode rpc` as strict stdin/stdout JSONL;
that is a better first machine interface for Ouvrier too.

## Ouvrier-Native Tools

The agent should not primarily edit blindly. It should use Ouvrier-native
tools that encode the framework's API and operational rules.

Required tools:

### Workspace

- `list_workers(root)`;
- `open_worker(path)`;
- `scaffold_worker(name, trigger, model, dir)`;
- `read_worker_manifest()`;
- `update_worker_manifest(patch)`;
- `checkpoint(label)`;
- `rollback_checkpoint(id)`;
- `git_status()`;
- `git_diff(paths?)`;
- `apply_patch(patch)`.

### Ouvrier API Knowledge

- `search_ouvrier_docs(query)`;
- `read_ouvrier_api(symbol)`;
- `list_ouvrier_primitives()`;
- `show_examples(name?)`;
- `validate_ouvrier_syntax(files)`.

The knowledge base is local and versioned:

- `README.md`;
- `docs/api.md`;
- `docs/handbook.md`;
- `docs/ouvrier-syntax-handbook.md`;
- examples;
- public API parity test output;
- generated scaffold templates.

### Worker Editing

- `add_tool(name, governance, schema, file?)`;
- `add_trigger(trigger)`;
- `add_pipe(goal, model, output_schema)`;
- `add_skill(name, body)`;
- `edit_file(path, patch)`;
- `format_go(paths?)`;
- `tidy_go_mod()`.

Where possible these tools reuse existing CLI/scaffold/edit code paths. They
must output normal Go, not a hidden DSL.

### Review And Audit

- `review_worker(scope)`;
- `review_diff(scope)`;
- `run_gate(name)`;
- `run_audit()`;
- `explain_gate_failure(gate_id)`;
- `fix_finding(finding_id)`.

### Runtime Probe

- `run_dev(port)`;
- `stop_dev()`;
- `admin_health()`;
- `admin_capabilities()`;
- `admin_trigger(payload)`;
- `tail_events()`;
- `trace_last()`.

### Build And Deploy

- `build_worker(target)`;
- `list_deploy_envs()`;
- `deploy_worker(env, target, env_file, keep)`;
- `rollback_deploy(env)`;
- `open_console(worker?)`.

Deploy always uses `internal/deploy`. The agent can propose deploy; the user
approves deploy.

## Prompt Pack

The Ouvrier prompt pack is the product's core advantage. It must make the
model an Ouvrier specialist.

It includes:

- the simple mental model: trigger, goal, tools, outcome;
- canonical snippets for HTTP, cron, webhook, stream;
- provider model naming rules;
- typed `Output[T]()` and `Reply(JSON[T]())` guidance;
- tool governance rules: `ReadOnly`, `SideEffecting`, `Idempotent`,
  `RequiresApproval`;
- sandbox and permission policy expectations;
- admin/observability endpoints;
- deploy and env-file rules;
- examples and anti-patterns.

Prompt pack injection is dynamic:

- short system-level invariant always loaded;
- relevant docs retrieved by symbol/query;
- scaffold template snippets loaded only when creating;
- deploy docs loaded only when transfer is requested;
- review rubric loaded only during review.

The agent should cite the local Ouvrier source file/doc it used in its plan
when it makes non-obvious API choices.

## Policy And Safety

Tool calls are classified:

```text
read-only
workspace-write
command
network
secret-read
build
deploy
destructive
```

Default policy:

- read-only tools run automatically;
- workspace writes require plan approval, then run within candidate workspace;
- commands are allowlisted by gate/tool type;
- network is denied except explicit runtime probes and deploy;
- secret reads require confirmation and are redacted;
- deploy requires explicit confirmation every time;
- production deploy requires second confirmation;
- destructive actions require explicit typed confirmation.

The harness must have an interrupt path. `Esc` during streaming aborts the
model/tool operation, records `interrupted`, and leaves the workspace in a
recoverable state.

Session features:

- continue latest;
- resume picker;
- fork session;
- append-only JSONL transcript;
- tree-shaped message history with parent/child IDs;
- model/thinking/profile change entries;
- branch summaries for forks;

- search transcript;
- mark findings accepted/dismissed/fixed;

## Build Strategy

The implementation should happen in vertical slices:

### Slice 0: Correct The Contract

- Mark v0.4.0 as a batch vertical slice, not the finished agent cockpit.
- Update docs so they do not over-promise a Pi/Codex-class terminal agent until
  the composer/runtime exists.
- Keep v0.4 subcommands as experimental shortcuts.

Acceptance:

- README/handbook distinguish current batch workflow from target cockpit;
- spec v0.5 is the acceptance source for the real agent harness.

### Slice 1: Real Composer And Session Loop

- Replace the v0.4 static cockpit with a prompt composer.
- Persist transcript and events.
- Add slash command parser.
- Add read-only tools: docs search, file read, worker detection.
- `ouvrier operate` can answer "what worker is this?" and "review this worker"
  inside one session.

Acceptance:

- user can type a prompt in TUI;
- model streams into transcript;
- read-only tools render as cards;
- session resumes after exit.

### Slice 2: JSONL RPC And Print Modes

- Add `ouvrier operate --print "prompt"` for one-shot automation.
- Add `ouvrier operate --mode json` for structured single-run output.
- Add `ouvrier operate --mode rpc` with strict JSONL stdin/stdout.
- All modes use the same `AgentRuntime` and session store as the TUI.

Acceptance:

- integration tests can drive the agent without terminal escape sequences;
- RPC can send prompt, steer, follow-up, interrupt, resume;
- TUI becomes a client of the same event stream, not a parallel implementation.

### Slice 3: Codex Login/Profile

- Add `/login codex`;
- probe official Codex CLI auth;
- store profile metadata only;
- model picker shows authenticated Codex models when available;
- friendly auth errors.

Acceptance:

- fresh machine guides user through login;
- authenticated machine starts without env vars;
- no Codex token appears in Ouvrier files/logs.

### Slice 4: Scaffold From Prompt

- Agent can call `scaffold_worker`;
- prompt pack teaches Ouvrier creation rules;
- missing-field questions appear in TUI;
- created worker is opened as session workspace.

Acceptance:

- natural language prompt creates compiling worker;
- transcript shows scaffold and file changes;
- worker remains ordinary Go.

### Slice 5: Edit/Plan/Diff

- Add plan approval;
- add workspace write tools;
- add checkpoint/rollback;
- show diff viewer.

Acceptance:

- agent modifies worker from prompt;
- user can inspect diff before audit/build;
- rollback returns to checkpoint.

### Slice 6: Review/Fix Inbox

- Structured findings;
- finding detail drawer;
- `fix selected` turns finding into scoped edit;
- accepted-risk rationale.

Acceptance:

- high finding blocks deploy;
- fixing finding reruns relevant gates;
- accepted risk is recorded.

### Slice 7: Build And Transfer

- Build tool calls existing build engine;
- deploy tool calls existing deploy engine;
- progress streamed into transcript;
- production confirmation.

Acceptance:

- user can prompt "build and deploy to staging";
- harness builds only after gates;
- deploy is never automatic without approval.

## Migration From v0.4.0

Current v0.4 code can be reused as lower-level services:

- session persistence;
- audit runner;
- review parser;
- build coordinator;
- transfer coordinator;
- Codex CLI probing;
- basic Bubble Tea colors.

But these must move behind the agent runtime. The new primary interface is:

```text
prompt -> model/tool loop -> visible tool cards -> diff/review/audit -> build/deploy
```

not:

```text
subcommand -> one function -> print summary
```

Headless subcommands may stay later as automation shortcuts, but they are not
the defining product.

Concrete v0.4 gaps to close:

- no multiline prompt composer;
- no steer/follow-up/abort;
- no real `plan` turn or `plan.md`;
- no candidate worktree by default;
- no structured transcript/tool cards;
- no Ouvrier docs/API retrieval tools;
- no tool registry exposed to the model;
- no review inbox or finding-specific fix path;
- no JSONL RPC mode;
- no first-class Codex login/profile flow;
- weak redaction around raw model outputs.

## Non-Goals

- Browser-based coding IDE.
- Hosted Ouvrier builder service.
- Remote build farm.
- Forking Pi TypeScript into the Go runtime.
- Storing ChatGPT/Codex subscription tokens directly.
- Allowing the model to deploy to production without explicit operator
  approval.
- Replacing Ouvrier's existing runtime harness.

## Acceptance Criteria

1. `ouvrier operate` opens a terminal agent cockpit with a prompt composer.
2. A natural language prompt can create a new worker from scratch.
3. The agent has Ouvrier-native tools, not just shell/edit.
4. The agent can inspect local Ouvrier docs/API and apply that knowledge.
5. Codex auth works through a first-class `/login codex` or official Codex CLI
   bridge; no Codex token is stored by Ouvrier.
6. Sessions are resumable and exportable.
7. Tool calls stream into visible, collapsible cards.
8. Edits require plan approval and produce inspectable diffs.
9. Review findings are structured and actionable.
10. High/critical findings block deploy unless accepted with rationale.
11. Build uses the existing Ouvrier build engine.
12. Transfer uses the existing deploy engine and requires approval.
13. The web console remains unchanged as fleet/worker observation.
14. `go test ./...`, `go vet ./...`, and relevant TUI model tests pass.

## Product Bar

If the user cannot sit in `ouvrier operate`, type what they want, watch the
agent create or modify a worker, review the code, fix issues, build, and deploy
without leaving the cockpit, the feature is not done.
