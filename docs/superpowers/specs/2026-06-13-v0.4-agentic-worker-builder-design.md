# Design: v0.4 "Agentic Worker Builder"

**Date**: 2026-06-13
**Status**: proposed
**Type**: feature milestone (SOTA local agentic builder harness, CodexDriver, Bubble Tea operator TUI)

## Vision

v0.3 made Ouvrier workers deployable, scalable, and observable. v0.4 makes
workers fast to **create, review, fix, build, and transfer** from one local
operator interface without changing the worker runtime model.

The builder harness is a first-class Ouvrier product surface. It must be
state-of-the-art for local agentic software construction: streaming,
interruptible, resumable, inspectable, sandboxed, audit-gated, human-approved,
and built around ordinary source code. It is not a thin shell wrapper around an
LLM command, and it is not a fake "agent loop" that treats a final text answer
as completion.

The user-facing model is:

```text
operate -> audit/review -> build -> transfer
```

- **Operate**: choose or create a worker, describe the desired tool/pipeline
  change, run an agentic patch loop, and keep the result as ordinary Go code.
- **Audit/review**: inspect the diff, run deterministic gates, ask the agent to
  review the diff, and optionally loop fixes until the gates pass.
- **Build**: compile the worker through the existing build engine and record a
  local artifact with provenance.
- **Transfer**: call the existing deploy engine (`ouvrier deploy <env>` path)
  after the operator explicitly approves the audited candidate.

Ouvrier owns the workflow, audit policy, artifact ledger, and deployment
boundary. Codex is only the local coding agent driver behind that workflow.

MVP cuts: no embedded Pi, no web IDE, no server-side Codex auth, no remote build
agents, no public Ouvrier runtime API changes, no automatic production deploy
after an agent patch, no hidden generated worker format.

## Product Boundaries

The v0.4 architecture keeps four surfaces separate:

- **Builder harness**: local workspace orchestration, agent turns, diffs, audit
  gates, review, build artifacts.
- **Deploy engine**: existing `internal/deploy` transfer machinery, systemd
  layout, SSH host-key pinning, health gate, rollback, inventory.
- **Web console**: existing fleet/worker observability over SSH tunnels and
  `/admin/*`; it may display deployed state but does not become a coding IDE.
- **Worker runtime**: unchanged trigger -> goal -> tools -> outcome execution
  path.

PI is not vendored into Ouvrier. Its useful idea is the cockpit pattern: a local
agentic interface with commands, skills, tools, and inbox-like feedback. v0.4
reimplements the narrow Ouvrier-specific cockpit in Go with Bubble Tea and a
CodexDriver.

The UI should strongly draw from PI's interaction model while staying native to
Ouvrier: persistent sessions, a chat/command composer, streamed agent/tool
events, collapsible tool output, diff-first review, right-side overlays for
inbox/details, keyboard-driven selection, model/thinking indicators, and a
compact terminal-native visual language. PI is a reference experience, not a
runtime dependency.

## SOTA Harness Invariant

Every shipped v0.4 builder flow must execute through a real internal harness
with explicit components:

1. `BuilderHarness` - coordinator for one operate session.
2. `BuilderSession` - durable per-session state, goal, driver, branch,
   candidate workspace, audit status, build artifacts, trace IDs, and
   cancellation.
3. `WorkspaceManager` - project discovery, candidate worktree creation,
   in-place safety checks, path validation, and cleanup.
4. `AgentDriver` - the only path for Codex or future coding agents to plan,
   patch, review, and fix.
5. `PromptPack` - Ouvrier-specific construction guidance, source references,
   and output schemas.
6. `PatchTracker` - diff capture, file-change summaries, patch artifacts,
   conflict detection, and apply/keep/abandon decisions.
7. `AuditRunner` - deterministic gates, command execution, timeouts,
   structured failures, and fix-loop budgeting.
8. `ReviewRunner` - read-only agentic code review with severity, file/line
   findings, and finding-to-fix conversion.
9. `BuildCoordinator` - build artifact creation through `internal/deploy`,
   provenance capture, and binary hash recording.
10. `TransferCoordinator` - deploy handoff through the existing deploy engine,
    deploy confirmation policy, progress streaming, and post-transfer status.
11. `OperateEventStream` - append-only local event stream for TUI rendering,
    session replay, debug logs, and future console read-only views.
12. `OperatePolicy` - deterministic authorization for edits, commands, network,
    secret exposure, transfer overrides, and production deploys.

No agent edit may bypass `AgentDriver`. No file mutation may bypass
`WorkspaceManager` and `PatchTracker`. No build or transfer may bypass the
existing deploy/build engines. No user-visible log, session artifact, review,
or trace may bypass redaction. No acceptance should treat a text-only Codex
answer as a completed patch unless the candidate diff, gates, and operator
approval prove it.

## Command Surface

New top-level command:

```sh
ouvrier operate [--dir .] [--agent codex|manual] [--codex-mode auto|exec|app-server] [--session ID] [--goal TEXT]
```

Initial behavior is interactive. The command opens a Bubble Tea TUI and refuses
fully unattended agent edits. Existing headless commands (`new`, `add`,
`build`, `deploy`, `status`, `logs`, `trace`) remain the automation surface for
CI.

Flags:

- `--dir`: project root or workspace root. Defaults to `.`.
- `--agent`: `codex` by default when the `codex` binary is available and usable;
  `manual` runs the same audit/build/transfer workflow without an agent.
- `--codex-mode`: `auto` chooses the best available Codex transport, `exec`
  uses `codex exec --json`, `app-server` uses `codex app-server` JSON-RPC.
- `--session`: resume a prior local operate session.
- `--goal`: pre-fill the first task prompt; the operator still confirms the
  plan and patch application in the TUI.

Deferred subcommands:

```sh
ouvrier operate audit --dir .
ouvrier operate review --session ID
ouvrier operate review-worker --dir .
ouvrier operate resume ID
```

These are useful later for CI or scripting, but the v0.4 MVP should first prove
the interactive harness.

## TUI Workflow

The TUI uses Bubble Tea v2 and follows the existing Ouvrier visual identity:
black/off-white/phosphor green, monospace, restrained boxes, no decorative
animation.

Primary screens:

1. **Workspace**
   - Detect Ouvrier projects by `pip.yaml`, `main.go`, and
     `ouvrier.worker.json`.
   - Offer `open existing` or `create new`.
   - For creation, call `internal/scaffold.Generate` or the same code path as
     `ouvrier new --yes`; do not duplicate scaffold templates.
   - Show Git branch, dirty state, detected deploy environments, and current
     worker manifest.

2. **Goal**
   - Collect the operator's plain-language change request.
   - Offer templates: new worker, add tool, add trigger, add skill, fix failing
     gate, review current worker.
   - Inject Ouvrier-specific guidance into the agent turn: worker remains normal
     Go, use `ovr` public API, prefer existing `ouvrier add` commands where
     they fit, keep public runtime API unchanged.

3. **Review Worker**
   - Review the current worker without making edits.
   - Let the operator choose scope: whole worker, current diff, one pipeline,
     one tool, deploy readiness, security/governance, or failing trace.
   - Run Codex in read-only mode and return structured findings.
   - Any finding can be converted into an explicit fix turn after operator
     approval.

4. **Plan**
   - Run a read-only agent turn that produces a concise plan.
   - Show intended files and commands before any write.
   - Require operator approval before patching.

5. **Patch**
   - Run the agent in a candidate workspace with write permission.
   - Stream agent events, command executions, and file changes into the TUI.
   - Show the resulting Git diff. The diff is the artifact; there is no opaque
     generation format.

6. **Audit**
   - Run deterministic gates in the candidate workspace.
   - Failures are shown as structured gate results.
   - The operator can ask the agent to fix failures, with the failed gate output
     as context.

7. **Review**
   - Run a read-only Codex review of the final diff.
   - Findings are structured by severity with file/line references when
     available.
   - High or critical findings block transfer unless the operator explicitly
     overrides.

8. **Build**
   - Call `internal/deploy.Build` / `StaticBuild` rather than shelling out
     independently.
   - Record binary path, target, sha256, Go version, Git revision, session ID,
     and gate status.

9. **Transfer**
   - List deployable environments from `pip.yaml`.
   - Call `deploy.DeployEnvironment` with the same option resolution as
     `ouvrier deploy <env>`.
   - Stream progress in the TUI.
   - Reuse the existing production confirmation behavior and add one extra
     confirmation when deploying from an unmerged candidate branch.

## UI Reference: PI-Inspired Ouvrier TUI

The `operate` UI is not a generic wizard. It should feel like a dedicated
agentic coding cockpit for Ouvrier workers, strongly inspired by PI's terminal
experience:

- **Persistent conversation rail**: a main transcript that shows the operator
  goal, agent plan, tool/command execution, patch summaries, audit results,
  review findings, build output, and transfer progress in chronological order.
- **Composer-first interaction**: a bottom command/prompt composer with
  multiline input, queued follow-up/steering behavior, model/thinking display,
  and explicit mode indicator (`review`, `operate`, `fix`, `build`,
  `transfer`).
- **Collapsible tool blocks**: command output, tests, build logs, Codex events,
  and deploy streams appear as compact blocks with status, elapsed time, and
  expand/collapse behavior.
- **Diff-first patch review**: added/removed/context lines are color-coded,
  navigable, and tied to the files changed in the current candidate workspace.
- **Right-side overlays**: use PI-like overlay panels for worker manifest,
  session details, review finding detail, audit failure detail, deploy target
  confirmation, and session resume picker.
- **Inbox-like findings**: review findings and audit failures behave like an
  actionable inbox: open detail, mark acknowledged, convert to fix, dismiss
  with recorded rationale.
- **Session tree/resume**: sessions are resumable and navigable by workspace,
  branch, status, and timestamp. Forking a session is deferred but the data
  model should not preclude it.
- **Keyboard-first controls**: keep common keys familiar from PI-style TUIs:
  arrows/page navigation, `enter` to confirm, `escape` to cancel/back,
  `ctrl+c` to clear/interrupt, `ctrl+d` to exit on empty composer, `ctrl+o`
  to expand/collapse tool output, `ctrl+p` or equivalent to cycle/show model,
  `shift+tab` or equivalent to cycle displayed reasoning effort when supported.
- **Terminal-safe layout**: every rendered line must fit the terminal width;
  narrow terminals degrade to one-column flow; overlays hide or resize rather
  than overlapping content.
- **Ouvrier visual identity**: black, off-white, phosphor green `#00d27a`,
  monospace, restrained borders, clear success/warning/error states, no
  decorative animation.

Before implementing non-trivial UI screens, take local reference captures from
the installed PI experience and keep them with the design notes. PI is already
available in the development environment; use its docs, exported sessions, and
interactive screens as reference material. When building browser-rendered
mockups, console adjuncts, or exported session views, verify layout with
Playwright CLI screenshots across desktop and narrow widths. Store temporary
captures under `docs/superpowers/mockups/operate-ui/` or `/tmp`, and do not
commit screenshots unless they are intentionally added as design references.

## Candidate Workspace Model

Agent edits must not silently rewrite the operator's active worktree.

Default behavior for an existing Git repository:

- Require a clean working tree before starting an agent patch session.
- Create an isolated Git worktree under `.ouvrier/operate/worktrees/<session-id>`
  on branch `ouvrier/operate/<session-id>`.
- Run Codex and audit gates inside that candidate worktree.
- Keep the original worktree untouched until the operator chooses one of:
  - apply patch back to the original worktree;
  - keep the operate branch for manual review;
  - deploy from the candidate branch after a local commit and explicit
    confirmation.

For non-Git projects:

- `operate` can scaffold and build normally.
- Agent edits to an existing project require an explicit `in-place` confirmation
  in the TUI. The session still writes a patch artifact before and after the
  edit so the user can audit what changed.

Dirty worktree support is deferred. The error should be actionable:

```text
operate requires a clean Git worktree before agent edits; commit, stash, or run
manual mode.
```

## Builder Session Store

Session data lives under the project-local `.ouvrier/operate/sessions/<id>/`
directory. The directory is mode `0700` when created.

Files:

- `session.json`: state machine, paths, branch, timestamps, selected driver,
  current status.
- `goal.md`: operator prompt.
- `plan.md`: approved agent plan.
- `codex.jsonl`: redacted event stream from the driver.
- `diff.patch`: candidate diff after each patch turn.
- `audit.json`: gate results.
- `review.json`: structured review findings.
- `build.json`: build artifact metadata.
- `transfer.json`: deploy target and final outcome.

No Codex auth cache, API key, worker admin token, SSH private key, or dotenv
secret may be copied into the session store. Command output is redacted before
it is persisted.

Session state machine:

```text
new -> selected -> planned -> patching -> patched -> auditing
    -> audit_failed -> patching
    -> reviewed -> built -> transferred
    -> abandoned
```

Every transition is append-only in `session.json` so `ouvrier operate --session`
can resume after a crash without inventing state.

## CodexDriver

`CodexDriver` is an internal driver behind a small interface. The builder
harness must be testable with a fake driver; no package outside the operate
subsystem should depend on Codex-specific types.

Sketch:

```go
type Driver interface {
    Probe(ctx context.Context) (Capabilities, error)
    RunTurn(ctx context.Context, req TurnRequest, sink EventSink) (TurnResult, error)
    Close() error
}
```

`TurnRequest` includes:

- `Kind`: `plan`, `patch`, `review`, `fix`.
- `CWD`: candidate workspace.
- `Sandbox`: `read-only` for plan/review, `workspace-write` for patch/fix.
- `Prompt`: operator goal plus Ouvrier guidance.
- `ContextFiles`: selected paths to summarize or attach.
- `OutputSchema`: optional JSON Schema for plan/review results.

`EventSink` receives normalized events:

- agent message delta;
- command started/completed;
- file changed;
- warning/error;
- final result;
- token/usage metadata when available.

### Codex transports

The driver supports two transports behind the same interface:

1. **`exec` transport**
   - Runs `codex exec --json`.
   - Uses explicit sandbox flags: read-only for plan/review, workspace-write
     for patch/fix.
   - Parses JSONL events and maps them to `EventSink`.
   - Good MVP path: simple process boundary, easy fake-runner tests.

2. **`app-server` transport**
   - Runs `codex app-server` over stdio JSON-RPC.
   - Initializes with client metadata such as `name=ouvrier_operate`.
   - Starts/resumes Codex threads for richer streaming and follow-up turns.
   - Preferred long-term path for a first-class TUI, but it must stay behind
     the same driver interface so `exec` remains a reliable fallback.

`--codex-mode=auto` starts with `app-server` only when the local Codex version
and transport probe are known to work; otherwise it uses `exec`.

### Codex auth

Ouvrier does not own Codex authentication.

- The driver uses the operator's local Codex CLI installation and whatever
  authentication it already has: ChatGPT subscription login, enterprise access
  token, or API-key backed Codex auth.
- Ouvrier never parses, copies, stores, or uploads `~/.codex/auth.json`.
- Ouvrier never sets `OPENAI_API_KEY`, `CODEX_API_KEY`, or a ChatGPT access
  token on behalf of the user.
- If Codex reports an auth failure, the TUI shows an actionable message:
  install Codex if missing, then run `codex login` or the appropriate
  organization-approved login flow.

This keeps subscription and workspace policy inside Codex, while Ouvrier owns
only the local builder workflow.

## Ouvrier Prompt Pack

The harness injects a compact Ouvrier-specific prompt pack on every agent turn.
It is not a public skill system; it is internal guidance for worker construction.

Rules:

- The worker must remain a normal Go project using the public module
  `github.com/ArnaudGuiovanna/ouvrier`.
- Prefer existing CLI helpers (`ouvrier new`, `ouvrier add trigger`, `ouvrier
  add tool`, `ouvrier add skill`, `ouvrier build`) when they fit.
- Do not expose or edit internal Ouvrier runtime packages from a generated
  worker.
- Keep `ouvrier.worker.json`, `pip.yaml`, `main.go`, `tools/`, and `skills/`
  consistent.
- Tool governance must be explicit: read-only tools use `ReadOnly()`,
  mutating tools use `SideEffecting(...)` or `Idempotent(...)`, and dangerous
  work uses `RequiresApproval()`.
- Generated code must compile, be gofmt'd, and be readable by a human.
- Secrets are never written into source, manifests, logs, prompts, or tests.

The prompt pack should cite the local sources of truth by path (`README.md`,
`docs/api.md`, `docs/handbook.md`, `docs/ouvrier-syntax-handbook.md`) rather
than embedding stale copies.

## Audit Gates

Audit gates run in the candidate workspace after every patch turn. Gates are
structured and independently visible in the TUI.

Required gates:

1. `git diff --check`
2. `gofmt` check or formatting pass followed by a diff refresh
3. `go test ./...`
4. `go vet ./...`
5. `ouvrier build --static --target linux/amd64 --dir <candidate>`
6. manifest coherence: `pip.yaml`, `main.go`, and `ouvrier.worker.json` agree
   on name, admin URL defaults, trigger class, and expected outcomes
7. secret scan over the candidate diff for obvious committed secrets

Recommended warning gates:

- `staticcheck ./...` when available on `PATH`;
- unclassified tool registration warning when a generated tool lacks
  `ReadOnly`, `SideEffecting`, `Idempotent`, or `RequiresApproval`;
- deploy-readiness warning when `go.mod` points at a local Ouvrier checkout
  while the operator is preparing a remote transfer.

The operator can ask for a fix loop. The default automatic fix loop budget is
two patch turns per audit run. More iterations require explicit confirmation.

## Agent Review

Agent review is separate from deterministic gates and has two modes:

1. **Worker code review**: review an existing worker even when no patch session
   is active.
2. **Candidate diff review**: review the final diff before build or transfer.

- Review runs read-only against the selected scope and relevant worker files.
- Output is schema-shaped:

```json
{
  "findings": [
    {
      "severity": "low|medium|high|critical",
      "file": "tools/load_ticket.go",
      "line": 42,
      "title": "Missing idempotency guard",
      "body": "..."
    }
  ],
  "summary": "..."
}
```

- High or critical findings block transfer by default.
- The operator can convert a finding into a fix turn.
- The operator can override the block, but the override is recorded in
  `review.json` and `transfer.json`.

### Worker code review mode

`operate` must support reviewing a worker's source code without first asking
for a new feature. This is a first-class mode for maintenance and audit.

Scopes:

- whole worker;
- changed files only;
- one tool;
- one pipeline/trigger;
- governance/security review;
- deploy-readiness review;
- failing runtime trace or event payload when supplied by the operator.

The review prompt must inspect Ouvrier-specific risks:

- invalid or brittle trigger/pipeline composition;
- missing tool descriptions or weak JSON parameter shapes;
- missing `ReadOnly`, `SideEffecting`, `Idempotent`, or `RequiresApproval`
  semantics;
- secrets in code, manifests, tests, prompts, or logs;
- unsafe filesystem, network, subprocess, or approval behavior;
- mismatch between `pip.yaml`, `ouvrier.worker.json`, `main.go`, and deploy
  environments;
- untested public behavior;
- generated code that will be hard for a human to audit.

Each finding can be turned into one of these actions:

- `fix_with_ai`: starts a patch turn scoped to the finding and its file set.
- `explain`: asks Codex for a read-only explanation of why the finding matters.
- `mark_accepted_risk`: records a local rationale and unblocks transfer only
  when policy allows.
- `dismiss`: records that the operator considers it non-actionable.

AI modification after review always follows the normal patch path: candidate
workspace, diff, audit gates, optional review, build, and transfer. The review
mode must not directly edit files.

## Build Artifact

Build uses the existing deploy/build package, not an ad hoc shell path.

`build.json` records:

- project name;
- candidate workspace path;
- binary path;
- target;
- sha256;
- Go toolchain version;
- Git branch and revision;
- dirty/candidate diff hash;
- operate session ID;
- audit and review status.

If the candidate workspace is dirty, build may proceed, but transfer warns
loudly. Production transfer should require a local commit on the candidate
branch so the release has a stable Git revision.

## Transfer

Transfer is not a new deploy engine.

The harness calls the same code path as `ouvrier deploy <env>`:

- environment resolution from `pip.yaml`;
- env file validation;
- host-key pinning;
- static build when needed;
- release layout upload;
- systemd install/restart;
- health gate;
- rollback;
- inventory update.

The TUI adds orchestration around it:

- choose deploy environment;
- show target hosts;
- show gate status;
- require confirmation;
- stream progress;
- offer to open `ouvrier console` after success.

No transfer is allowed when required gates failed unless the operator uses an
explicit override. Production overrides require a second confirmation.

## Console Relationship

The existing web console remains an operations surface:

- fleet list and tunnel state;
- worker status, plans, traces, approvals, events;
- manual trigger;
- streamed deploy;
- remote-friendly access through SSH tunnels.

v0.4 may add links from `operate` to launch the console after deploy, but the
console does not host the builder harness and does not receive Codex tokens.

Future work may add a read-only "operate sessions" page to the console, backed
by local session artifacts, but it must not become a browser-based coding
surface in v0.4.

## Security Model

- Codex only runs locally on the operator machine.
- Codex runs in a candidate workspace, not on production hosts.
- Codex gets `read-only` sandbox for plan/review and `workspace-write` sandbox
  for patch/fix. `danger-full-access` is out of scope for v0.4.
- Ouvrier never stores Codex credentials, API keys, SSH keys, worker admin
  tokens, or dotenv secret values in session artifacts.
- All persisted command output is redacted through the same token-redaction
  discipline used by deploy/tunnel code.
- Candidate paths are validated to stay under the project root or the
  `.ouvrier/operate/worktrees` root.
- Browser console routes remain protected by their existing token, origin,
  host-header, no-cookie, and allowlist model; no Codex route is added there.

## Package Layout

Expected internal packages:

- `internal/operate`: session state machine, workspace management, audit
  orchestration, build/transfer orchestration.
- `internal/operate/driver`: driver interface and normalized events.
- `internal/operate/codex`: CodexDriver transports and process/JSONL or
  JSON-RPC parsing.
- `internal/tui/operate_*`: Bubble Tea screens and models.
- `internal/cli/operate.go`: flag parsing and command entrypoint.

Existing packages reused directly:

- `internal/scaffold` for new worker creation.
- `internal/cli` add helpers may be refactored into reusable packages only when
  needed; do not duplicate unsafe string-edit logic in the harness.
- `internal/deploy` for build and transfer.
- `internal/adminapi` and `internal/tunnel` only for optional post-deploy status
  checks or console handoff.

## Acceptance Criteria

1. `ouvrier operate` opens a Bubble Tea workflow that can create or select a
   worker and run a complete local operate -> audit -> build path.
2. With a fake driver, CI can exercise the full workflow deterministically
   without Codex.
3. With `CodexDriver`, a local operator can request a worker change, review the
   generated diff, run gates, ask for fixes, and build the resulting binary.
4. `operate` can review an existing worker without a pending patch, produce
   structured findings, and convert an approved finding into a normal AI fix
   turn.
5. Transfer uses the existing deploy engine and cannot bypass deploy's env,
   host-key, health-gate, or rollback behavior.
6. Session artifacts are local, human-readable, redacted, and resumable.
7. The UI demonstrates PI-inspired cockpit patterns: transcript, composer,
   collapsible tool blocks, diff review, right-side overlays, review inbox, and
   keyboard-first operation.
8. The existing web console behavior and runtime public Go API remain unchanged.
9. `go test ./...`, `go vet ./...`, staticcheck, and relevant TUI/CLI golden
   tests stay green.

## Deferred Work

- Browser-based builder UI.
- Remote build machines or hosted Ouvrier builder service.
- PI integration as a supported driver.
- Multi-agent builder swarms.
- Deterministic replay of Codex turns.
- Automatic PR creation/push.
- Fully unattended `operate --yes --deploy` automation.
- Managed enterprise policy for which Codex workspaces/models may be used.
