Synthese

OK
Le noyau runtime est reel.

Declaration publique, compilation en plans, dispatch HTTP/Cron/Stream/Mixed, harness agentique, tools gouvernes, schemas, et admin endpoints sont implementes et couverts.

OK
Les tests passent localement.

Commande lancee: GOCACHE=/tmp/go-build-cache go test ./.... Tous les packages listables sont passes.

Partiel
Quelques preuves sont conditionnelles.

Postgres, Bubblewrap, sshd et certains builds croises ont des tests qui se sautent sans environnement dedie.

Gaps
Peu de non-implementation explicite.

Le principal manque explicite est operate --codex-mode=app-server. Il y a aussi des incoherences DLQ/rediss detaillees plus bas.

Conclusion courte: Ouvrier n'est pas un simple squelette. La trajectoire critique "trigger -> goal -> tools -> outcome" traverse du code concret, avec tests. Les zones a surveiller sont surtout des limites d'integration, de validation et de maintenabilite, pas une absence generale d'implementation.

Architecture mentale

Le modele utilisateur reste volontairement court: trigger, goal, tools, outcome. Le runtime concret est cache derriere cette syntaxe, mais pas absent: chaque Pipe passe par internal/harness, internal/tools, internal/policy, internal/events et internal/state.

Frontieres de propriete

Le package racine ovr expose le contrat public et garde les structures lourdes internes. Les packages internal/* portent les implementations substituables: providers, state stores, deploy, console, tunnel, operate cockpit, TUI et IDE.

Sequence concrete

  1. Le DSL public construit des Node immuables: From, Pipe, Parallel, Map, Reply, Push, Sink.
  2. compile.go valide l'ordre des nodes, les compatibilites trigger/terminal, les options de trigger, et injecte le schema Reply(JSON[T]) dans le dernier Pipe si besoin.
  3. runner.go construit le runtime par defaut: provider registry depuis l'environnement, store depuis OUVRIER_STATE_*, event stream, admin token, durable-run config.
  4. Le runner refuse les surfaces admin exposees hors loopback sans opt-in, puis choisit newHTTPCompatibleHandler, serveCronPlans, serveStreamPlans ou serveMixedPlans.
  5. Chaque trigger transforme l'entree en JSON de travail, reserve l'idempotency si configuree, cree/charge une session, et appelle runPlanResultWithSession.
  6. http_runtime.go enregistre les tools du step dans un tools.Executor scope: Go funcs, Bash, SubAgent et MCP. Le provider est resolu par prefixe provider/model.
  7. internal/harness lance la boucle LLM: budget, streaming, fallback, tool calls, schema validation/repair, session/events/state.
  8. Les actions de sortie Push et Sink(File) repassent par un output tool interne pour appliquer la PermissionPolicy. Sink(Log) est redige avant d'etre journalise.

Outputs, queues et sinks

Reply

OK JSON[T], SSE(), Accepted(). JSON typed est reconcilie avec Output[T]. SSE consomme les events de token deltas.

Push

OK Webhook HTTP et queues http(s), nats, kafka, redis/rediss, sqs. Les pushes passent par permission policy.

Sink

OK Log redige via EventStream; File ecrit sous sandbox et demande une autorisation target file.

Redaction et traces

Les events sont sanitizes dans event_stream.go. Les payloads sensibles, tokens, secrets, cookies, bearer et assignments ressemblant a des credentials sont masques avant exposition admin, traces, state store et hooks.

Ce qui n'est pas completement ou correctement implemente

Cette section liste les vrais points noirs observes dans le depot local. Certains sont des limites volontaires documentees; d'autres sont des incoherences de validation ou de surface.
Point Type Impact Preuve Action recommandee
operate --codex-mode=app-server Non implemente Le mode est visible dans l'aide mais inutilisable. L'utilisateur doit utiliser auto ou exec. internal/cli/operate_flags.go Soit implementer le transport app-server, soit retirer/masquer le mode dans l'aide jusqu'a livraison.
Validation StreamDLQ trop restrictive Incoherence La DLQ runtime peut publier vers http(s), sqs, rediss, mais l'API publique les rejette a la validation. trigger.go utilise validateStreamURI; runtime_stream_dlq.go accepte davantage de schemes. Creer un validateur dedie DLQ/queue target, et ajouter des tests pour sqs://, https://, rediss://.
rediss:// stream trigger Support incomplet Le dialer Redis sait faire TLS, mais Stream("rediss://...") n'est pas accepte par la validation ni par le switch receiver. runtime_stream_redis.go, trigger.go Accepter rediss dans validateStreamURI et defaultStreamReceiver.Receive, avec tests.
Custom public StateStore sans durable-run journal Limite volontaire Un store public custom peut faire le runtime courant, mais ne peut pas activer OUVRIER_DURABLE_RUNS=1. runner_state.go Documenter explicitement dans l'API, ou exposer une interface publique etendue pour les stores durables.
DLQ replay ne draine pas les topics broker arbitraires Limite documentee Le replay admin draine la copie runtime retenue, pas un topic Kafka/NATS/Redis/SQS externe independant. runtime_stream_dlq.go, docs/api.md Ajouter des consumers DLQ broker-specifiques si le produit veut rejouer depuis broker reel.
NATS stream sans ack durable Limite de transport Le receiver NATS lit un message via protocole core; pas de JetStream durable/ack visible. Manual ack peut devenir no-op. runtime_stream_nats.go, trigger.go Clarifier dans docs, ou ajouter JetStream si c'est l'attente produit.
Validation URL webhook push tardive Validation faible Webhook(url) comme Push target n'est valide que non-vide au compile-time; URL invalide echoue au POST. trigger.go, runtime_http.go Parser et limiter a http/https dans validatePushTarget.
Exemples avec stubs Volontaire Ne pas interpreter les exemples comme integrations metier completes. ticket-triage, moodle-fsrs Conserver l'avertissement dans README; eventuellement ajouter un exemple avec vraie integration.
Fichiers tres volumineux Maintenabilite La navigation est plus difficile dans routes.go, runtime_http.go, internal/tui/operate.go, internal/harness/harness.go, etc. routes.go 1918 lignes; runtime_http.go 1202; internal/tui/operate.go 1137; internal/tunnel/manager.go 919. Refactorer par responsabilite uniquement quand une modification touche la zone; eviter un gros split mecanique sans tests.
Preuve locale des integrations externes Preuve conditionnelle Le run local prouve le code et les fakes, pas un vrai broker, un vrai host SSH, ni un vrai provider LLM. Tests conditionnels: Postgres DSN, sshd, Bubblewrap, cross-compile short mode. Ajouter un job d'integration optionnel ou nightly avec brokers/sshd/provider mocks plus proches production.
